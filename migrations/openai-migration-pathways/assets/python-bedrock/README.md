# Bedrock application adapters

The Responses JSON adapter reads the generated `approved-routes.json` alongside `bedrock_json_agent.py`. Copy both into the application. Its exact model/endpoint/Region/scope choices come from the reviewed nine-model catalog. Use a full model slug such as `gpt-6.1-sol`; legacy aliases `sol`, `terra` and `luna` retain their GPT-5.6 meaning. Do not infer identifiers from a family name.

`inference_scope` accepts `in-region`, `us`, `in` or `global` only when the exact catalog route exists. Provisional entry Regions are excluded from this transport export. New catalog support does not establish account access or application feature parity. The adapter is a non-streaming Responses helper with application-owned history and local validation/repair. It does not implement native schema enforcement, hosted tools, streaming, or distributed state. A request-time token supplier remains required for credential refresh.

Model/API documentation was reviewed October 14, 2026; see the registry and [catalog](../../docs/compatibility-catalog.md). The application-specific adapters below retain their narrower, dated verification scope. Their presence is not evidence of a newly tested customer deployment.

## Client-side function tools

`BedrockToolAgent` adds a client-side function loop; `BedrockJsonAgent` stays no-tool. Register each function with a `ToolBinding`: name, description, Pydantic argument model (`extra="forbid"`), async handler and whether it can mutate state. The handler receives validated arguments and the model's call ID. Bind caller identity, resource scope, authorization and any required approval in the application closure, not model arguments. Kernel objects and arbitrary tool names are not discovered or executed automatically.

The loop validates all calls in a response before executing the batch sequentially. It rejects unknown tools, duplicate IDs/argument keys, invalid arguments, refusals, incomplete responses and hosted-tool items. Defaults allow eight tool calls and six model calls per turn, with one output-schema repair and a shared deadline. Model calls during repair/finalization disable tools. Returned reasoning, function calls and matching `function_call_output` items are carried forward with `store=false`.

If a turn fails after admitting a mutating callback, the thread is retired even when its local history is unchanged. Cancellation awaits cooperative handler cleanup. Neither behavior undoes external effects: inspect/reconcile the application's actual state before starting a new thread, and implement durable idempotency for external writes. This is not a distributed transaction or a hard timeout for callbacks that ignore cancellation. Read-only classification is a trusted application contract, not inferred from a function name.

`thread.tool_receipts` exposes detached local records of tool name, call ID, effect classification and completion/uncertainty status, without argument or result payloads. These records survive a failed turn in the current process so the application can identify operations requiring reconciliation. They are not durable execution receipts or proof of remote effects.

The Customer Assist source includes explicit bindings for its nine form setters. They update a private form copy and validate the complete result before replacing the current form. Each update requires the application's authorization callback; marking an address verified additionally requires application-owned verification evidence.

The application composition registers all 13 tools: nine form setters, loan-policy retrieval and three document analyzers. Its agent factory and conversation consumer share one form and one local thread. The default Customer Assist profile now selects Bedrock for the assistant, sentiment and post-call agents, with no Azure chat service. Worker startup supplies conversation-authorized dependencies and rejects runtime configurations that switch an active agent back to an unsupported provider. Local tests execute application definitions with controlled providers and a process-builder double; they do not prove complete service import/startup or live deployment.

Assistant output uses a strict result schema before conversion to UI state. It cannot report a verified document without application-approved form state, or return loan-policy insights before retrieving policy evidence. Unknown numeric policy terms remain null; legitimate zero values remain zero. A successful retrieval is not proof that generated policy terms are grounded correctly: retrieval-quality and answer-grounding evaluation are still required.

Function message format: [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling). AWS documents client-side tools on both Responses endpoints; actual model/account execution remains a separate verification step.

## Loan-policy retrieval

`knowledge_base_search.py` queries an existing Bedrock Knowledge Base through the AWS SDK's `bedrock-agent-runtime` service. It does not generate text or change the approved model route. The application binds a knowledge-base ARN and an async authorization callback; the model supplies only the search text. Bind exact metadata constraints for restricted corpora, or explicitly select a shared corpus. Filters accompany every page, and returned metadata must match before any document text is released. Document ingestion and metadata administration must be controlled by trusted identities; metadata alone does not authenticate a user.

The adapter requests semantic retrieval and returns text, stable citation IDs, source references and scores. It supports S3 and HTTPS web citations without fetching them. Retrieved text is evidence, not application instructions. Unknown content types, credential-bearing/query-string citations, mismatched metadata and guardrail intervention cause errors. No-match results stay empty; result/page limits are flagged as truncated. Context exceeding the byte budget is rejected rather than silently shortened.

Each query creates and closes its SDK client in the same worker thread using the configured AWS credential chain. Cancellation stops further pagination and waits for the current SDK operation to finish cleanup; it cannot forcibly interrupt a blocking SDK call. No automatic application retry is performed. Grant the task role `bedrock:Retrieve` only on the selected knowledge base and the dependent permissions required by its configured backend.

Customer Assist's `bedrock_loan_policy_search.py` registers this adapter as a read-only `loan_policy_search` tool. Worker configuration binds its ARN and corpus metadata; the conversation grant must permit policy retrieval. Offline tests cover the real application binding, tool loop and AWS SDK request/response shapes. Creating the knowledge base, choosing an approved embedding policy, migrating/indexing policy documents, retrieval quality and live IAM access remain separate work. SDK dependencies are application requirements, not plugin installation requirements.

API contract: [AWS Retrieve](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Retrieve.html), checked 2026-09-03.

## Document extraction

`textract_documents.py` supports the current sample's single-page document-image flow. Utility bills and income statements use fixed Textract Queries; US driver's-license images use AnalyzeID. Source utility-bill/license field names are preserved. No income-statement schema was found in the source repository, so its employee, employer, gross-income and pay-period fields are an explicit proposed mapping, not verified parity with the former service.

The application registers opaque handles bound to a bucket, object key, non-null S3 version, document kind, validated size/format and applicable jurisdiction. `register_document` lets the trusted upload path add new documents during a conversation without replacing existing handles. It is not a model tool. Each analysis requires the application-owned authorization callback. Model-supplied URLs, bucket names, versions and unregistered handles are never fetched. Upload registration must verify the actual object metadata and conversation owner; do not register claims copied from an untrusted request.

Results preserve values and normalized confidence. Missing, conflicting, partial and below-80%-confidence fields require review. OCR never sets `identity_verified=true`: matching text and confidence are not proof that a document is genuine or belongs to the applicant. Address verification continues to require the separate application-owned evidence/approval callback. License addresses include street, city, state and postal code; an incomplete combination is explicitly partial.

This synchronous adapter accepts one page up to 10 MB; multi-page document processing remains an explicit gap, not silent first-page extraction. The default AWS image-admission route has a stricter 5 MB PNG/JPEG limit. SDK clients use the configured AWS credential chain, fixed Region and bounded network waits. Cancellation waits for owned SDK cleanup; it cannot forcibly cancel a remote Textract operation. Tests validate API shapes and local error handling, not OCR accuracy or live permissions.

Customer Assist's three `bedrock_document_tools.py` bindings preserve the former analysis wrapper names. Their `file_uri` parameter now carries the registered handle, not a signed URL. The default AWS session path passes these handles through the internal queue contract, and the process registers newly uploaded documents before invoking the assistant.

Sources checked 2026-09-03: [AnalyzeDocument](https://docs.aws.amazon.com/textract/latest/APIReference/API_AnalyzeDocument.html), [AnalyzeID](https://docs.aws.amazon.com/textract/latest/APIReference/API_AnalyzeID.html), [identity fields](https://docs.aws.amazon.com/textract/latest/dg/identitydocumentfields.html), [document limits](https://docs.aws.amazon.com/textract/latest/dg/limits-document.html).

## Upload ownership and worker handoff

`document_uploads.py` connects application ingress to the document analyzer. Import it alongside `textract_documents.py` in the application's utilities package. `ConversationDocuments` binds a trusted principal, session and server-owned thread to fixed S3 storage settings and a shared Redis registry. Its constructor does not authenticate those values: the ingress authentication layer must supply them. Browser payload fields and model arguments are not identity evidence.

Provide async `authorize(scope, operation)` and `approve_content(bytes, media_type)` callbacks. Operations are `conversation`, `upload`, `publish` and `read`. The Customer Assist handler rechecks conversation access for every message, rejects a different claimed user, and never creates an Azure thread on this path. Document reads recheck current access and registry availability on every tool call, including already registered handles.

The uploader decodes and fully checks one PNG/JPEG image, at most 10 MB and 40 million pixels, before content approval. It creates a private S3 object under the conversation prefix, uses a conditional write, then verifies the returned version through a version-specific metadata/checksum read. Only then does it publish an opaque handle using a no-replace, expiring Redis record. The worker checks scope, storage boundary and version before atomically adding a document batch. A repeated identical registration is allowed; rebinding a handle is not. Client metadata never supplies internal document handles.

Registry records require private, authenticated Redis access and separate ingress/worker ACLs; they are not cryptographic attestations against a privileged registry writer. Expiration or record deletion disables future resolution, but does not delete S3 data. Failed/cancelled uploads may leave private objects or a registry entry if publication was already committed; no URL is returned and no automatic deletion is attempted. S3 retention/orphan cleanup is an operator policy. Application upload limits and content moderation still need deployment-specific settings.

Pillow and boto3 are application dependencies, not plugin installation requirements. The reviewed application requirements pin Pillow 12.3.0 and boto3 1.43.81. S3 permissions include conditional upload and version-specific reads; KMS-encrypted checksum retrieval requires the relevant KMS permissions. The existing hosting module needs its document-reader role/prefix permissions wired before this path can run in AWS. Local tests cover API request shapes, scope isolation, publication failures, cancellation cleanup and the actual ingress-to-worker handoff; they are not live IAM, OCR or authentication tests.

The download helper resolves an existing handle, fetches only its registered S3 version, checks the expected bucket account, length, content type, scope metadata and SHA-256 checksum, then rechecks the current registry grant before returning bounded bytes. It closes the response stream and SDK client even on failure or cancellation. It does not create public or presigned URLs. Serve returned bytes with private/no-store caching and attachment disposition; never accept storage keys from the browser.

S3 API contracts: [PutObject](https://docs.aws.amazon.com/boto3/latest/reference/services/s3/client/put_object.html), [HeadObject](https://docs.aws.amazon.com/boto3/latest/reference/services/s3/client/head_object.html), [GetObject](https://docs.aws.amazon.com/boto3/latest/reference/services/s3/client/get_object.html), checked 2026-09-03.

## Authenticated application sessions

`alb_identity.py` verifies the signed `x-amzn-oidc-data` claim from a configured commercial AWS Application Load Balancer. It accepts ES256 only, pins the load-balancer ARN, issuer and client ID, validates the header expiry, and derives the principal from the verified subject. Unsigned `x-amzn-oidc-identity` and browser user IDs are not authentication evidence. It supports ALB's padded JWT encoding. Signing keys come only from the configured Region's AWS key endpoint, with bounded downloads and cache size; redirects and environment proxies are disabled.

`conversation_grants.py` issues short-lived grants under server-generated thread IDs. The trusted ingress chooses explicit permissions; no grant can authorize document verification. Workers check the private registry on each request. Expiration, revocation, missing records and registry failures deny access. This is a registry-backed authorization contract, not a defense against an administrator who can rewrite grant records. Use separate ingress write/revoke and worker read-only ACLs. A lost publication response can leave a grant until its bounded expiry; credentials and access tokens are never copied into it.

`authenticated_sessions.py` composes identity verification, exact browser-origin checks, grants and document ownership. The Customer Assist HTTP/WebSocket handlers accept this runtime through `app["aws_session_runtime"]`. `/api/identity` returns only the derived user ID and expiry with `Cache-Control: no-store`; the frontend must use that identity when sending messages. The WebSocket path revokes its own grant on exit or failed admission. A reconnect receives a new server-owned thread. Both the ingress and worker recheck scope and authorization; existing connections do not silently outlive the grant.

Local tests verify real ES256 signatures and the actual loopback HTTP/WebSocket handlers, including duplicate headers, origin rejection, expiry, revocation and competing connections. Session and worker startup own registry clients with credentials distinct from their queues; local TLS Redis tests verify writer/read-only/queue isolation. The hosting template includes the authentication action and the browser uses the identity endpoint before connecting. Protected backend traffic must originate from the configured ALB and use HTTPS. Application HTTPS startup, deployed ACLs and the complete browser login still need verification. Application dependencies are PyJWT 2.13.0 and cryptography 50.0.1, not requirements for installing the Codex plugin.

Authority: [AWS ALB user-claim verification](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html), checked 2026-09-03.

## Default application startup

`aws_session_runtime.py` builds the ingress runtime from deployment settings and uses Rekognition image moderation before S3 writes. It rejects any returned moderation label at the configured 80% request threshold; missing responses, required human review and provider errors do not admit an image. This is a content-admission policy, not document authenticity verification. The worker uses `agents/aws_runtime.py` to bind the same registry/storage scope and its loan-policy knowledge base. It checks the conversation grant before configuration loading, and again before processing; form and retrieval tools check their narrower permissions. Workers do not receive upload/publish permission through this helper.

Both services require `DOCUMENT_REGISTRY_NAMESPACE`, `AWS_REGION`, `AWS_ACCOUNT_ID`, `S3_IMAGE_BUCKET` and the same ingress-owned `S3_IMAGE_PREFIX`. They also require separate `AUTHORIZATION_REDIS_USERNAME`/`AUTHORIZATION_REDIS_PASSWORD` settings in addition to queue credentials; see [registry ACLs](../python-redis/authorization-registry.md). Ingress additionally requires `S3_IMAGE_KMS_KEY_ID`, `ALB_SIGNER_ARN`, `OIDC_ISSUER`, `OIDC_CLIENT_ID` and `APPLICATION_ORIGINS` (a JSON list of exact HTTPS origins). The worker additionally requires `LOAN_POLICY_KNOWLEDGE_BASE_ARN` and `LOAN_POLICY_CORPUS`. Model transport requires its configured Bedrock API key. These are customer application deployment settings, not Codex plugin installation settings.

The current patch does not yet replace the browser's Azure speech integration or map legacy source-page URLs to authorized AWS downloads. `/get-speech-token` explicitly returns 501 and `/content/{path}` returns 404 rather than making Azure calls or serving an unowned document. These remain application feature gaps, not evidence of complete migration. The browser now supplies authenticated identity and document kind; generated service permissions, full imports/builds and live validation are still required.

The updated Customer Assist patch exposes registered upload downloads at `GET /api/documents/{handle}?session_id={active_session}`. It verifies the signed identity against the active session owner, checks the document grant before and after storage reads, and returns an attachment with private/no-store and nosniff headers. Missing authentication returns 401; unavailable, foreign or revoked documents return the same 404. This endpoint covers registered uploaded PNG/JPEG documents, not arbitrary Knowledge Base citations or legacy source-page paths. It requires the matching application patch; copying the helper alone does not add an HTTP route.

Content API: [Rekognition DetectModerationLabels](https://docs.aws.amazon.com/rekognition/latest/APIReference/API_DetectModerationLabels.html).
