# Background worker ownership

For Python queue consumers that already have cooperative async processing, adapt `../../../assets/python-workers/worker_pool.py`. Each worker receives a stop event, stops polling when it is set, and finishes an item already acquired before returning. The pool retains every created task, reports unexpected exits, and requests peer shutdown on failure. A service can use `healthy` to fail its health check when processing has stopped; this is not a complete downstream-dependency readiness probe.

Stop intake before draining. In aiohttp, request worker stop in `on_shutdown` and await pool cleanup before closing Redis in `on_cleanup`. The helper waits up to 30 seconds, requests cancellation, then waits another five seconds by default. If tasks remain active it returns false; do not release resources they still use. Partial-start failures retain their created tasks for cleanup. The pool cannot restart after stop.

Those are pool deadlines, not a guarantee for the whole process: the framework, SDK clients, cancellation-resistant tasks and telemetry retries can extend teardown. Coordinate server drain, task stop timeout and collector ordering. Call trace flush/shutdown after successful framework cleanup, including ordinary server failures. Verify real termination behavior in the built application.

Do not describe this as queue durability. Redis LPOP still removes an item before processing, and cancelling an active job can lose it. Keep acknowledgment/replay, idempotency and failover as separate application capabilities. Nor does this helper automatically own pub/sub listeners, WebSocket connections or customer SDK clients; inspect those separately.

The helper's standard-library tests are in `tests/test_worker_pool.py`. Application-specific tests must also exercise actual worker callbacks, poll-versus-stop boundaries, failed-worker health, resource ordering and the framework shutdown path.

For existing Redis pub/sub services, adapt `../../../assets/python-redis/redis_subscriptions.py`. It accepts an owned Redis client, waits for subscription acknowledgments, dispatches callbacks serially, and exposes listener failure through `healthy`. Callback errors are isolated; transport failure stops the listener. Close it before its Redis client, and retain resources if `close()` returns false. Startup failure, cancellation and cleanup retries keep their task/connection handles. This does not add durable delivery, replay or automatic service restart.

For WebSocket services, stop session admission before taking the shutdown snapshot. Register a connection before upgrade, reject duplicates without removing the original, and remove entries only when that same connection owns them. Return the prepared framework response, join message processors before closing their shared producers/SDK clients, and guard partial initialization. Preserve each application's error/correlation contract; malformed input must not crash a secondary error handler. Test a real local WebSocket lifecycle as well as the Redis helper. Reconnect recovery, identity and delayed-response correlation require separate application tests.

For serialized request/reply services on Python 3.11+, adapt `../../../assets/python-workers/request_tracker.py`. Create one tracker per connection and one fresh internal attempt ID per request; public dialog IDs may be reused. Carry the ID through queue schemas, workers, progress, final and error replies. Match request/session/dialog/thread/user before serialization. Complete the waiter only after the socket write; errors are terminal even without an answer. Always finish the attempt in a finally block. Include enqueue and delivery in the response deadline. This confirms an awaited server write, not browser receipt or exactly-once delivery.

Cached orchestrators must receive the current reply handler per call; overwriting a shared handler can reroute an older workflow's progress. Check internal worker/session protocol compatibility during rollout—strict matching cannot accept legacy replies without attempt IDs. Correlation does not cancel already-queued work or protect shared agent/chat state from concurrent execution. Test backend state isolation, authentication and durable recovery separately.
